# Part II — Cleaning

> The full code for this phase is in the accompanying notebook. This document explains the reasoning and findings.

These datasets are quite clean, since they were synthetically created to be analyzed. Even so, I examined whether it was convenient to follow the basic cleaning actions needed in most datasets.

## 1. Structural Arrangements

As seen in the profiling phase, there are no wrong headers in any table. There are also no empty rows in the "dfaccounts" table, since there were no empty values during profiling.

Regarding empty rows in "dftransactions", I suspected there were no empty values (because we are working with a synthetic dataset), but I confirmed it anyway — "dftransactions.isna().any().any()" returns "False".

Both tables do have column names with a blank space separating words, so it is necessary to join them, because PostgreSQL works better with single names than with spaces. I chose "snake_case" to rename all columns.

## 2. Data Type Conversion

### 2.1. "dfaccounts" Type Conversion

Out of these columns, the only conversion I would make is Bank ID (now "bank_id") to string. Since it is an ID, I am not going to perform numerical operations with it, and I think it is cleaner to have coherence in data types: every column serving as an identifier will be an object / string type for further operations.

### 2.2. "dftransactions" Type Conversion

Following the same criterion as in 2.1, I converted "from_bank" and "to_bank" to string type. I also converted "timestamp", which was of type object, to a proper datetime type. Finally, the identification column I had added in the previous phase ("id"), which was of type int, was converted to string as well, to keep coherence across identifier columns.

## 3. Filtering

Filtering at this stage means removing rows or columns that are not relevant to the analysis — this is a matter of scope, not data quality (duplicates and nulls are handled separately).

**Row filtering:** I am not filtering rows at this stage. Whether any subset of transactions should be excluded depends on the requirements of the typology analysis, which comes later. Since the substantive analytical criteria are not yet defined, any row-level filtering decision is deferred to that phase.

**Column filtering:** The "is_laundering" column was removed from the working dataset. The goal of this project is to detect suspicious transactions independently, so this label is kept aside as a separate validation key rather than used as an input to the analysis.

**Privacy / PII:** This dataset is synthetic, so it contains no real personal data and no privacy or data-governance constraints apply. In a real AML context, however, columns such as entity names and account numbers would constitute sensitive information subject to data-protection requirements, and handling them would require appropriate governance measures.

## 4. String Cleaning

The standard string-cleaning steps (trimming, internal-space and non-printable normalization, casing, variant unification, orthographic correction, and abbreviation normalization) were considered but are not required here. Being synthetic — generated by a simulator rather than entered by humans — the dataset does not present the inconsistencies these steps are designed to correct.

## 5. Nulls and Duplicates

I have already seen there are no nulls in any table.

Regarding duplicates, there are duplicates in the transactions table, which is not inherently wrong, but it is worth checking their magnitude. I dropped the "id" column for this check, because otherwise it would trivially return "False" (the surrogate key makes every row unique).

There are 16 duplicates (8 pairs) over more than 6.9 million rows, which is negligible. Besides, it is possible, since "timestamp" measures minutes and not seconds — two genuine transactions between the same accounts within the same minute would look identical. These were kept.

## 6. Final Validation

I checked both tables' shape: "dfaccounts" is (712,688, 5) and "dftransactions" is (6,924,049, 11). Neither the number of rows nor columns changed in either table. I also confirmed that column names were correctly changed to "snake_case" and that the column types are as intended (identifiers as object/string, "timestamp" as datetime, amounts as float).

## 7. Closing

This cleaning phase confirmed that the datasets required very little correction. There were no nulls, no wrong headers, no empty rows, and no string inconsistencies to fix. The only duplicates found were 16 rows in the transactions table, which are valid transactions and were kept.

The changes I made were: renaming all columns to "snake_case", converting identifier columns to string, converting the timestamp column to datetime, and adding a surrogate key to the transactions table. The final validation confirmed that no rows were lost and that all types and names are as intended.

The data is now clean and ready for the next phase.
